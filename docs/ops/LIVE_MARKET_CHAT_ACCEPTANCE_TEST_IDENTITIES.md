# Live Market Chat — owner-controlled test identities

## Why this exists

Authenticated Live Market Chat write-path acceptance requires **two disposable,
non-production identities** restricted to channel `acceptance_test`.

Automated unit/RLS/failover coverage is already green (PR #223 / #225 / #226).
**Live authenticated posts must not use the production owner account** and must
not invent users on the production Supabase project without an explicit
owner-approved staging auth surface.

## Current inventory (as of 2026-11-10)

| Surface | Finding |
|---|---|
| Supabase projects in org | **One** — `QuantForg` / `otqyhlmwaifokrczryrc` (production) |
| Isolated / staging Supabase project | **None** |
| Railway `staging` environment | Exists, but **no** `SUPABASE_URL` / keys configured |
| Approved test identity env vars | **None** (`TEST_*` / `E2E_*` / `ACCEPTANCE_*` absent) |
| `scripts/provision_admin_user.py` | Admin bootstrap only — **not** for chat acceptance identities |

**Do not** create chat acceptance users against production Supabase until an
isolated staging project (or owner-signed exception) exists.

## Owner procedure (secure)

### A. Preferred — dedicated staging Supabase project

1. In the Supabase org, create project `QuantForg-Staging` (separate from
   `otqyhlmwaifokrczryrc`).
2. Apply chat migrations:
   - `supabase/migrations/20261110180000_live_market_chat.sql`
   - `supabase/migrations/20261110180100_live_market_chat_rls.sql`
   - plus required helpers (`current_app_user_id`, `users`, etc.).
3. Configure Railway **staging** with that project's `SUPABASE_URL`,
   `SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY` (never into Vercel
   `NEXT_PUBLIC_*` except the anon/publishable key).
4. Deploy the API to Railway staging pointing at staging Supabase only.
5. Provision **two** disposable users via Supabase Auth Admin **on staging**:
   - Example emails: `chat-accept-a@example.test`, `chat-accept-b@example.test`
   - Passwords generated by the owner vault (length ≥ 16); never commit/print.
   - Confirm email / mark confirmed in staging only.
   - Ensure corresponding `public.users` rows exist (same path as normal signup
     or an owner-approved staging seed script).
6. Store for the acceptance agent (local secret store / shell env only):
   - `QF_CHAT_ACCEPT_A_EMAIL` / `QF_CHAT_ACCEPT_A_PASSWORD`
   - `QF_CHAT_ACCEPT_B_EMAIL` / `QF_CHAT_ACCEPT_B_PASSWORD`
   - `QF_CHAT_ACCEPT_API_BASE` = staging API base (`…/api/v1`)
7. Authorize the agent to post **only** to channel `acceptance_test`.

### B. Temporary exception (owner-signed only)

If the owner explicitly authorizes production Supabase for disposable chat
users:

1. Put written approval in the PR / ops ticket (scope: chat acceptance only).
2. Create two disposable users with non-owner emails.
3. Same env var names as above, with `QF_CHAT_ACCEPT_API_BASE` set to
   production API.
4. Delete/disable the users immediately after cleanup.

This path is **not** the default and must not be assumed.

## Acceptance exercises (once identities exist)

All posts must use `channel=acceptance_test` (never public `xauusd`).

1. Login A → `POST /market/chat` succeeds; response `user_id` matches session.
2. Spoof body fields cannot change `user_id`.
3. Empty / oversized / control-character bodies rejected.
4. Burst posts → `rate_limited`.
5. `POST /market/chat/{id}/report` requires auth; works for A.
6. With B: cross-user UPDATE/DELETE via PostgREST denied by RLS; A cannot
   mutate B's rows.
7. Anon read of `acceptance_test` still works; anon write still 401.

## Cleanup

1. Soft-hide or remove acceptance rows (`status` → `hidden`/`removed`) via an
   authorized staging admin/service path — not anon.
2. Disable or delete disposable Auth users on the **staging** project.
3. Unset local `QF_CHAT_ACCEPT_*` env vars.
4. Confirm `acceptance_test` message count is 0 (or only retained audit fixtures
   the owner wants kept).
